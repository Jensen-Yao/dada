# 抖音机制反哺搭搭（LBS · 消息 · 沉浸式）

> 视角：抖音同城/消息方向资深开发。对照对象：`web/public/js/pages/discover.js`（推荐流）、`conv.js`（聊天）、`server/src/db.js`（schema）。
> 结论先行：**最赚的是已读回执（后端已就绪，纯前端活）和附近搭局 tab（city 字段+索引现成）**；全屏上滑流不适合搭子场景，做"详情页下一个推荐"折中。

## 一、同城/LBS：抖音的精髓与搭搭的"附近搭局"

抖音同城三件套的本质：**距离是决策信息不是装饰**（"2.3km"直接决定去不去）、城市切换器解决"异地浏览/出差"场景、同城热榜制造"身边正在发生"的时效感。搭搭的搭局天然强 LBS（饭搭/运动搭半径通常 <5km），比抖音更需要它。

现状：`posts` 表只有 `city TEXT`（已有 `idx_posts_city` 索引）+ `location_name` 文本，无坐标。工程方案分三期，**不要一步上坐标**：

1. **P1 城市粒度（先上）**：广场顶部加城市切换器（复用用户 `city`，登录态默认、可手切，存 localStorage）；"附近搭局" tab = `WHERE city=? ORDER BY created_at DESC`，走现成索引零改造。卡片角标展示 `location_name` 文本（"朝阳大悦城"比"3.2km"更具体）。再加"本城热榜"＝按 city 过滤的热门排序。
2. **P2 可选精确定位**：H5 `navigator.geolocation`（需 HTTPS+用户授权，失败静默回落 profile city，坐标存 localStorage 复用 7 天）；`posts` 加 `lat REAL, lng REAL` 可空列（CREATE IF NOT EXISTS 幂等加列，老数据为 NULL）。发布时逆地理一次写入；老帖**懒回填**——仅在进入"附近"请求且 `location_name` 非空时，用免费地理编码（如高德 Web 服务 API）补坐标并缓存。
3. **P3 距离计算**：数据量小（单机 SQLite）直接 SQL haversine 排序即可：
   `6371*acos(cos(rad(?lat))*cos(rad(lat))*cos(rad(lng)-rad(?lng))+sin(rad(?lat))*sin(rad(lat))) AS dist`，前端显示 `dist<1 ? (dist*1000|0)+'m' : dist.toFixed(1)+'km'`。量级上来再换 geohash 前缀分桶。隐私红线：**永不展示对方精确坐标，只展示帖子到我的距离**。

## 二、消息体验差距：按投入产出排序

| 能力 | 投入产出判断 | 依据 |
|---|---|---|
| **已读回执** | ★★★★★ 立刻做 | **`messages.read_at` 列已存在**，`chat.js:80` 拉取消息时已在写。只差：消息列表接口回传 `read_at`、WS 推 `peer_read` 事件（对方进会话时通知）、发送方气泡下渲染"已读/未读"小字。找搭子是强时效撮合，"对方看了没回"是核心焦虑，半天工作量 |
| **气泡表情回应** | ★★★★ 值得做 | 对气泡长按/双击弹小表情条（😂👍❤️），`messages.type` 加 `reaction` 或独立 `message_reactions` 表（msg_id+user_id+emoji，UNIQUE 防重）。抖音/微信都在用，解决"不想尬聊但想给反馈"——搭子破冰期刚需 |
| **Web Push 离线推送** | ★★★ 有条件做 | 技术可行：PWA 的 `sw.js` 已在，加 `push` 事件监听 + VAPID 密钥 + `PushSubscription` 表 + `web-push` npm 包。**硬约束**：iOS 需 16.4+ 且"添加到主屏幕"后才收得到；国内 Android 浏览器杀后台严重，到达率不稳。搭搭是撮合型产品（申请通过/满员/新消息），离线召回价值高，但要有"到达率打折"预期，别当核心链路 |
| **@提醒** | ★★ 暂缓 | 搭搭当前是 1v1 会话，无私聊群/评论区@场景；等搭局群聊（roadmap 已列）上线再一起做，现在做是无的放矢 |

## 三、沉浸式浏览：上滑详情流适合搭子吗？

**判断：不适合，别做全屏上滑流。** 抖音成立的前提是"零决策消费"——内容 15 秒、上滑成本趋近 0、算法承担全部筛选。搭局是**高决策对象**：时间/地点/费用/人数/性别限制/发起人履历，用户浏览目标是"比较后排除"，不是"kill time"。全屏单列会：①单帖占满屏幕反而降低比较效率；②搭局图文长尾内容填不满一屏；③误触上滑即跳走，打断正在读规则的认真用户。瀑布流（现状）+ 匹配徽章（MT-03 已做）才是对的信息密度。

**折中方案（值得抄的半步）**：详情页底部悬浮"下一个推荐 →"按钮——预取推荐队列（复用 `/for-you` 或按同 city+同分类取 3-5 条），点击后原地替换详情内容（不 push 路由，`history.replaceState`），并支持桌面端 ←/→ 键翻。保留沉浸感的"看不完"体验，又不剥夺用户的比较控制权；顺便把"看了 N 个"埋点收上来，为后续推荐冷启动攒数据。

## 四、可落地功能建议（按 ROI 排序）

1. **消息已读回执**｜要点：`/chat/conv/:id/messages` 回传 `read_at`；对方 open 会话时 WS 广播 `peer_read{conv_id, up_to_msg_id}`；发送方气泡下 10px 灰字"已读/送达"。价值：撮合核心焦虑可视化，拉回访。成本：**0.5 天，后端零 schema 变更**。
2. **附近搭局 tab（城市粒度）**｜要点：首页 tab 切"推荐/附近"，附近=city 过滤+`location_name` 角标+城市切换器；`idx_posts_city` 现成。价值：搭子第一决策因子是距离，补上最大的一块板。成本：1-2 天纯前端+一个 query 参数。
3. **详情页"下一个推荐"**｜要点：详情页预取同 city/同分类队列，原地替换+键盘支持+浏览埋点。价值：低成本获得"刷"的连续感，提升详情页深度。成本：1 天。
4. **气泡表情回应**｜要点：`message_reactions(msg_id,user_id,emoji)` 表 + 双击气泡弹 4 表情 + 对方 WS 实时收到；默认给"哈哈哈/抱拳/加油"。价值：低压力破冰反馈，提升回复率。成本：2 天。
5. **Web Push 离线通知**｜要点：VAPID + `web-push` + sw `push` 监听，只推三类（申请通过/满员关闭/新私信），站内 `notifications` 表已可作为 payload 源。价值：离线召回（到达率打折：iOS 需装 PWA、国产浏览器不稳）。成本：2-3 天 + 强制 HTTPS。

> 落地顺序建议：1 → 2 → 3 先出一个版本；4/5 视留存数据决定。P2 精确定位等"附近 tab"数据验证用户真在意距离后再上。
